# Local Ollama + BigQuery Analytics

## Role-Based PoC

Sign in at `/login` with username `monitoring`, `investigation` or `admin`. Generated passwords are in the ignored owner-only `analytics_service/profile-logins.local.json`; existing user passwords are preserved. Passwords are salted scrypt hashes in the runtime configuration. Do not commit either file or share the passwords in screenshots. The query page has no sign-in form. The separate `/profile` page lists the authenticated user's permitted tables, countries and entity codes, with sign-out there.

| Profile | Permitted logical tables through authorized views |
| --- | --- |
| Monitoring | Party, AccountPartyLink, Transaction, InteractionEvent, PartySupplementaryData, RetailPartiesRegistration, CommercialPartiesRegistration |
| Investigation | Party, RiskCaseEvent, RiskScores, Explainability |
| Admin | Union of Monitoring and Investigation: the 10 distinct tables above; no administrative write permissions |

All three profiles cover Hong Kong (HK/HASE), United Kingdom (GB/HSBC), India (IN/HSBC), Taiwan (TW/HSBC), France (FR/HSBC), Poland (PL/HSBC) and Ireland (IE/HSBC), retaining existing contact-field exclusions. Each uses a different read-only BigQuery service account (`aml-monitoring-poc`, `aml-investigation-poc`, `aml-admin-poc`) with table-level Data Viewer grants only on its permitted authorized views, plus project Job User. None has direct source-table access. `RegisteredPartiesExport` and `ExportedMetadata` remain excluded, including for Admin. The server selects scope and principal from authenticated identity; request-supplied roles/scopes are rejected. The model sees only permitted schema, and the independent validator rejects forbidden resources even if generated by the model.

Restricted requests receive HTTP 403 with "You do not have the required access to answer this question." A conservative intent check recognizes clear restricted-table requests; ambiguous/negated mentions proceed to independent SQL validation. Physical forbidden table references in model output are classified as access errors even when the model reports schema validation failure. Other model/SQL errors retain their original categories. These user-facing checks never grant permissions or replace SQL validation and BigQuery IAM.

Run `.venv/bin/python -m analytics_service.local --port 8012`. The launcher prefers `config.roles.local.json` when it exists. The earlier broad demo configuration is retained as an administrator reference, but its bearer token is not configured in the active role service. No public deployment is enabled.

Role setup is explicit: `.venv/bin/python -m analytics_service.setup_roles` inspects, `--apply` provisions after approval, and `--verify-only` rechecks all 12 authorized views under each actual role principal plus a denied direct-source read. IAM propagation can delay verification; do not treat policy creation alone as verified access. Existing local passwords are never overwritten by rerunning setup.

Admin setup is separate: `.venv/bin/python -m analytics_service.setup_admin --apply`, only after explicit approval of the additional principal and grants. It preserves both existing role credentials, backs up the two private config files, and adds exactly their resource union. Running without `--apply` verifies an existing Admin account without changing IAM. Verification checks all 12 views, denied writes and denied direct-source access; its report is ignored `admin-access-verification.local.json`. If IAM propagation delays the initial check, rerun verification before restarting the app.

### Sessions and Questions

- Opaque HttpOnly, SameSite=Strict sessions expire after one hour, are revoked at logout/account switch, and reset on service restart. Browser storage does not hold passwords or bearer tokens. Unsafe cookie-authenticated requests require a same-origin custom header; there is no cross-origin API allowance. Sign-in attempts have a global 10/minute limit. HTTPS sets Secure cookies; loopback HTTP is for this local PoC only. Before any public deployment, use a production identity provider, TLS and a reviewed session/rate-limit store.
- FAQ contains saved questions and frequently repeated completed queries. The plus button saves a question; selecting a question copies it into the input without automatically executing it. Every subsequent execution is newly authorized.
- History stores the last 100 queries per identity and role, including completion status and timestamp, in ignored mode-0600 `workspace.local.sqlite`. Up to 50 saved questions are retained per identity and role. No SQL or result rows are stored there. Questions can contain sensitive text; this is a local demo store, not a production retention solution. Clear history removes that account's history and frequency counts, not saved questions. History survives restart; sessions do not.
- `/auth/login`, `/auth/logout`, `/auth/me`, `/workspace`, `/workspace/saved` and `/workspace/history` support the UI. Passwords, roles and SQL are not accepted on `/query`; it still accepts only a question. Signed-out users cannot read history or saved questions.

Real opt-in role browser check: `node analytics_service/tests/ui_roles.cjs` with Playwright on `NODE_PATH`, Chrome installed and the app running. This checks all three profiles and submits real BigQuery-backed questions. Unit tests additionally force forbidden model responses to prove the executor is never called.

## First Setup

Run from the repository root with Python 3.12 or newer:

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
ollama serve
# In another terminal:
ollama pull mannix/defog-llama3-sqlcoder-8b
gcloud auth application-default login
gcloud auth application-default set-quota-project 1076784773678
.venv/bin/python -m analytics_service.setup_local
```

The last command is read-only: it compares every live table, recursive schema and row count with the saved catalog/manifest, stopping on drift. It does not verify full row-content hashes.

After administrator approval, run `.venv/bin/python -m analytics_service.setup_local --apply`. This provisions twelve authorized views in `aml_analytics_demo`, a dedicated `aml-analytics-demo` service account, project BigQuery Job User, view-dataset READER, and an impersonation grant for the verified signed-in user on that account only. It enables the IAM, IAM Credentials and Cloud Resource Manager APIs if needed. No billing configuration, source table replacement, or public deployment is performed. Existing IAM/access entries are preserved. Unexpected existing views stop setup rather than being overwritten. API activation can take a few minutes to propagate; setup retries only explicit SERVICE_DISABLED responses, not permission denials or ambiguous mutations.

`1076784773678` is the verified numeric ID of this same project. Using the text ID as the ADC quota-project header caused misleading API-disabled errors during local setup; the numeric ID resolved them. OpenID user identity verification does not attach a Cloud quota header.

This local demo permits all seven entity-country scopes. Contact fields (addresses, phone numbers, emails, birth dates and IP addresses) are excluded. Separately verify that the execution principal has no direct base-table access or write permissions. For country-restricted users, provision separate filtered views and a distinct service account per scope; changing the displayed scope list is insufficient.

The earlier setup writes ignored, owner-only `analytics_service/config.local.json` and `analytics_service/access-token.local.json`. These are administrator reference files; the current role-based UI uses passwords instead. Do not commit either file or send credentials in chat. Re-running setup refuses to overwrite local configuration. Partial cloud setup can be rerun after its error is resolved, provided no local configuration was written.

## Start Locally

```sh
.venv/bin/python -m analytics_service.local
```

Open [AML Analytics](http://127.0.0.1:8011/ui/). The launcher starts the model on loopback port 8000 and analytics on 8011; it refuses occupied ports. Ollama must already be running. Ctrl-C stops both Python services. Use `--port 8012` for another UI port.

| Variable | Launcher value |
| --- | --- |
| `MODEL_BACKEND` | `ollama` |
| `OLLAMA_HOST` | `http://127.0.0.1:11434` |
| `OLLAMA_MODEL` | `mannix/defog-llama3-sqlcoder-8b` |

Google authentication uses local ADC, then impersonates the role's read-only service account. There is no Gemini key or Google credential in the browser. The current UI calls its same-origin analytics service with an HttpOnly session cookie.

## API and Boundaries

Authentication has its own login page; the stakeholder query page links to a separate profile page. Infrastructure labels are replaced with readable market names. Overview and Data table tabs show deterministic charts or 25-row pages of the already-returned result (not additional server pagination). Single measures use KPI values, time series use lines, and categorical comparisons use horizontal bars. Identifier lists and ambiguous dimensions remain tables. Exact decimal strings are retained in tables. Incomplete-result and other non-routine warnings stay visible; SQL, job IDs, schema version and full warnings remain available under Analysis details. Synthetic-data disclosures and the AI business-meaning review notice are always visible.

Optional real local browser verification: install Playwright outside runtime dependencies, then run `node analytics_service/tests/ui_smoke.cjs` with Playwright on `NODE_PATH`. It requires local Chrome, the running service on port 8012 and the ignored profile login file. It signs in as Monitoring, submits one real query and uses isolated browser-only rendering cases to check pagination, empty and partial results. No test fixtures are used by the live application.

| Route | Contract |
| --- | --- |
| `GET /health` | Process liveness only |
| `GET /status` | Authenticated model and authorized-view readiness |
| `POST /query` | Authenticated `{"question":"..."}`; client SQL/scope fields rejected |
| `GET /metrics` | Optional reviewed questions; not a free-form mode restriction |
| `/login` | Dedicated username/password login; active sessions redirect to analysis |
| `/profile` | Authenticated profile with server-derived permitted tables and countries |
| `/ui/` | Analysis page; signed-out visitors redirect to login |

The adapter adds backward-compatible `execution_mode` and `allowed_columns` fields to `/generate-sql`. Execution mode calls Ollama using native BigQuery STRUCT/ARRAY types and enums, without exemplar answers or fuzzy SQL repair. The local launcher defaults to FalkorDB, reusing main's hybrid lexical/semantic retrieval and one-hop REFERENCES/LINKS_TO expansion. Graph descriptions and relationships provide retrieval context; deployed types, enums and authorized columns remain authoritative. Graph failures stop generation rather than silently switching to catalog retrieval. Existing graph data is read, never rebuilt or changed.

Put `FALKORDB_HOST`, `FALKORDB_PORT`, `FALKORDB_USERNAME`, `FALKORDB_PASSWORD`, `FALKORDB_GRAPH`, and optionally `HF_TOKEN` in the ignored project-root `.env`. Never commit this file. The local setup uses the existing hosted graph and local Ollama; BigQuery still executes only independently validated SQL through the restricted service account. Rotate any credentials shared in chat. Install dependencies in a persistent project virtual environment with `python3 -m venv .venv` and `.venv/bin/python -m pip install -r requirements.txt`.

Catalog mode ranks schema names, descriptions, enum values and domain vocabulary to focus the model on relevant tables, retaining an account-owner bridge when needed. This is metadata retrieval, not a whitelist of questions or stored SQL answers. Retrieval can miss a needed table; such questions may require clarification. The independent execution validator still enforces the complete approved catalog.

A narrow AST normalization converts SQLCoder's known `DATE_TRUNC('month', timestamp)` argument order to GoogleSQL. It records corrections in the model response and never guesses identifiers or removes extra statements. Other invalid SQL is rejected; all normalized SQL still passes independent validation and a BigQuery dry run.

Candidates must pass one-read-only-statement, resource, function and schema checks. Table references are rewritten to authorized views. BigQuery performs a dry run before execution: configured 100 MB scan budget, 60-second execution deadline, best-effort cancellation, 1,000-row and approximately 2 MB response limits. Local inference has a configurable 240-second timeout with no automatic retry. These checks do **not** prove that arbitrary generated SQL matches business intent; review executed SQL for consequential analysis.

Responses carry typed columns, exact decimal strings, rows, executed SQL, request/job IDs, scan bytes, scope, data period, simulation warnings and deterministic charts. Tables preserve NUMERIC values; charts use approximate JavaScript numbers. Truncated results suppress charts. Ambiguous chart dimensions remain tables. No query results go back to the model. Empty results stay empty.

Party has historical versions; current-customer joins must deduplicate by latest `validity_start_time`. Risk-score periods must be explicit. Money uses normalized USD `units + nanos / 1e9`, not STRUCT-to-number casting. SAR events differ from distinct SAR cases. The prompt explains these rules; domain-owner review remains necessary.

Party aggregates without an explicit ROW_NUMBER snapshot are conservatively rejected, except pure min/max or distinct-ID-only queries. This blocks the observed duplicate-version count failure; it is not a proof of every temporal join. BigQuery dialect errors return a query-rejected response rather than claiming the database connection is down.

## Tests and Limits

```sh
.venv/bin/pip install -r analytics_service/requirements-dev.txt
.venv/bin/python -m pytest analytics_service/tests -q
```

Unit tests use explicit doubles/DuckDB fixtures isolated from the application. Live verification must exercise actual Ollama and BigQuery, compare gold values and verify IAM denials. Skipped live tests do not prove connectivity. See `VERIFICATION.md` for evidence and limitations.

No cloud compute, GPU hosting or public endpoint is deployed. Before network deployment, replace local bearer provisioning with approved identity, add TLS/ingress controls and centralized audit/rate limiting, and review SQL/model risks. Logs exclude raw questions, SQL, credentials and results. This is not a banking compliance certification or automated AML decision system.
